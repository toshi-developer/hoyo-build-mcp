# 引き継ぎ — 設計判断と未解決の検討事項（2026-09-17 更新）

このリポジトリを触る前に読む。**なぜそうなっているか**と、**まだ決めていないこと**をまとめる。

## 経緯

もともと崩壊：スターレイル専用の `hsr-build-mcp` として `~/hsr-build-mcp/` に作った。
その後「原神とゼンゼロもできるか」という話になり、Enka.Network が両方に対応していることを
確認して3タイトル対応に拡張。名前が実態と合わなくなったため `game-build-mcp` に改名し、
ワークスペースのサブモジュールとして git 管理下に移した。
その後リポジトリを公開するにあたり、`game-build-mcp` では「ゲームをビルドする」ツールと
誤読される（ワークスペース内に `game-monitor-agent` 等が並んでいたことも紛らわしかった）ため、
`hoyo-build-mcp` に再度改名した。

## 設計判断とその理由

### スタレだけ Mihomo のままにした

当初は「全部 Enka に寄せる」と提案したが、**変更した**。

Enka は **ID しか返さない**（`avatarId: 10000052` など）。原神・ゼンゼロは変換表
（`store/*.json`）を噛ませて日本語名に解決したが、スタレの Mihomo `sr_info_parsed` は
名前・ステータス・遺物のサブステと強化回数まで整形済みで返す。Enka に寄せると
自前で組み直すことになり**質が下がる**ため、データ元は使い分けた。

統一したのは入口（`build_*` ツールの `game` 引数）だけ。

### 名前を推測で埋めない

原神の聖遺物セット名のうち、Enka の辞書（`loc.json` / `gi/locs.json`）に **ja / en とも
載っていないものが2件**ある。名前を推測して書くと助言を誤らせるため、
`giSetLabel()` で次のように出している。

```
(未収録セットID:15020 / 2セット:元素チャージ効率+20.0%)
```

セット効果は `gi/relics.json` の `Sets[].AddProps` から機械的に導いているので正確。
**4セットか2セットかの判別も正しく効く**（グループ化は名前でなくハッシュで行うため）。

確認済みの未収録: `setId=15020`（2セット: 元素チャージ効率+20%）、
`setId=14003`（2セット: prop50 +0.4）。

### ZZZ の数値スケール

ZZZ のプロパティ値は ×100 で入っている（`HpMax_Ratio: 300` → 3.0%）。
`property.json` の `Format` に `%` が含まれるものを百分率として `/100` している。
**A ランクディスクの実値でしか検証していない**ので、S ランクや高強化での妥当性は未確認。

### ショーケースと HoYoLAB 戦績を併用している（2026-09-17 追加）

ショーケース（Enka / Mihomo）は **Cookie 不要だが、並べたキャラしか読めない**。
HoYoLAB 戦績は **所持キャラ全件を読めるが Cookie が要り、Cookie は期限切れになる**。
どちらかに寄せると失うものがあるので、`build_get_character` の `source` で選べるようにし、
既定の `auto` は「ショーケースに居なければ HoYoLAB」にした。応答には必ず `出典` を入れている。

**HoYoLAB は項目名を自分で返す**ので、Enka のような ID→名前の変換表が要らない。

| ゲーム | 名前を返す仕組み |
|---|---|
| 原神 | レスポンスの `property_map`、聖遺物は `set.name` と `affixes`（効果文つき） |
| ゼンゼロ | 各プロパティに `property_name`、ディスクは `equip_suit.name` と `desc1`/`desc2` |
| スタレ | レスポンスの `property_info`。遺物セット名だけは返らないので Enka の表で補う |

数値のままなのは3つだけで、いずれも**公開変換表と実データで裏を取ってから**定数にした。

| 対象 | 検証方法 |
|---|---|
| スタレ `base_type`（運命） | 所持35体を Enka `hsr/avatars.json` の `AvatarBaseType` と突き合わせ8種すべて一致。うち 6→存護 は Mihomo 出力とも一致 |
| 原神 `element`（Pyro 系） | 所持46体を Enka `gi/avatars.json` と突き合わせ7属性すべて一致 |
| ゼンゼロ `element_type` | 所持22体を Enka `zzz/avatars.json` と突き合わせ一致。日本語は `zzz/locs.json` の ja から取れる（`AddedDamageRatio_Physics` → 物理属性ダメージボーナス 等） |
| ゼンゼロ `avatar_profession` | 同じく突き合わせ一致。ただし**日本語の出典が無い**（`zzz/locs.json` の ja に該当キーが無い）ので Enka の英語表記のまま出している |

ゼンゼロは `x-rpc-language` を見ず **`x-rpc-lang`** を見る（両方送っている）。これに気づかないと
名前が英語で返る。

**HoYoLAB は原神の「未収録セット」を解決できる。** handover が挙げていた `setId=14003` は
「烈火を渡る賢者」で、2セット効果（炎元素耐性+40%）も `giSetLabel` の機械的導出と一致した。
両経路が相互検証された形になっている。

## 未解決の検討事項

着手するならこの順が効果的だと思う。

### 1.（対応済み 2026-09-17）所持キャラ全件の取得を原神・ゼンゼロにも広げる

Issue #1。`build_fetch_roster(game)` を追加し、`build_get_character` をショーケース外の
キャラにも対応させた。実データで確認済み（原神46体 / ゼンゼロ22体 / スタレ35体、
未解決IDゼロ）。`scripts/smoke.mjs` が19ケースの疎通確認を通す。

着手時点の記述と違っていた点を残す。

- `hsr_fetch_roster` は**一度も成功していなかった**。`HOYOLAB_COOKIE` が未設定で
  `roster/` も無かった。前セッションは DS 署名の確認までで終わっていた
- 原神は GET ではなく **POST** `/game_record/genshin/api/character/list`。
  詳細は POST `/character/detail` に `character_ids` を渡す
- ゼンゼロはホストが別（`bbs-api-os` ではなく **`sg-public-api`**）。
  詳細は `/avatar/info` に `id_list[]` を渡す
- リージョン体系がゲームごとに別物（`prod_official_asia` / `os_asia` / `prod_gf_jp`）。
  ゼンゼロだけ UID 先頭2桁で決まる

Cookie は `~/.hsr-build-mcp/.hoyolab-cookie` から読む（`HOYOLAB_COOKIE_FILE` で変更可）。
`claude mcp add -e HOYOLAB_COOKIE=...` は `~/.claude.json` とシェル履歴に平文で残るため。
`ltuid_v2` でなく **`ltmid_v2` + `ltoken_v2` でも通る**ことを実測で確認した。

**DS 署名ソルトが壊れたことに気づく手段が無い問題は未解決のまま。** Cookie の期限切れも
同じで、どちらも「使おうとして初めて気づく」。→ 検討事項7

### 2. データディレクトリが `~/.hsr-build-mcp/` のまま（要整理）

リポジトリ名・登録名・UA・`McpServer` の名前メタデータは `hoyo-build` 系に揃えたが、
**データディレクトリと環境変数だけスタレ時代の名前のまま**残っている。

- `~/.hsr-build-mcp/`（`HSR_DATA_DIR` で変更可）
- `HSR_LANG` / `HSR_REGION` は今もスタレ専用の設定なので、この2つは名前として正しい

`~/.hoyo-build-mcp` に寄せるなら、**既存のスナップショット履歴を移す処理が要る**。
勝手に消えると育成の記録が飛ぶので、起動時に旧ディレクトリがあれば引き継ぐか、
移行の手順を README に書くかを決めてからにする。今は据え置き。

### 3. テストが実データ頼み

`scripts/smoke.mjs` を足したが、**ネットワークと Cookie が要る**ので壊れた原因の切り分けに
使いにくい（自分のバグか、向こうの仕様変更か、Cookie 切れかが混ざる）。
当初の案どおり、**保存済みスナップショットを入力にした整形のスナップショットテスト**が
別に要る。`~/.hsr-build-mcp/snapshots/` と `roster/` に実データがあるので、
数件をリポジトリに固定して入力にすればオフラインで回せる。

### 4. 変換表キャッシュ7日の妥当性

新キャラ実装直後は7日待つと `(ID:...)` になる。`ttl` のように
サーバー側の指示に従う仕組みは無いので、手動更新の手段（`force` 引数）があってもよい。

### 5. 原神の天賦レベル表示

`meta.SkillOrder` の並び順で「通常攻撃 / 元素スキル / 元素爆発」に対応づけているが、
**旅人など複数の元素を持つキャラで正しいか未確認**。命ノ星座による +3 は
`proudSkillExtraLevelMap` から拾っているが、こちらも検証は1キャラ（ベネット C6）だけ。

### 6. エラー時の挙動

Enka が 424（ゲームメンテ中）を返すケースは**実際には踏んでいない**。
メッセージは用意したが、文言が実態と合うかは未確認。

### 7. HoYoLAB が壊れたことに気づけない（効果大）

ソルト変更（`retcode=-10001`）も Cookie 期限切れ（`-100` / `10001`）も、
**次に使おうとしたときに初めて分かる**。相談の最中に落ちると体験が悪い。
`build_fetch_roster` を叩いたときに Cookie の残り有効期間を記録しておく、
定期的に軽いエンドポイントを叩いて記録する、あたりが考えられる。

### 8. 原神・ゼンゼロは HoYoLAB を既定にすべきか

実データで比べると、**原神・ゼンゼロは HoYoLAB のほうが質が高い**。

- 原神: Enka で引けない聖遺物セット名が解決する（`setId=14003` → 烈火を渡る賢者）。
  セット効果も日本語の効果文つきで返る。命ノ星座の解放状況も分かる
- ゼンゼロ: 値が整形済みの文字列で返るので、**`×100` スケールの解釈が要らない**
  （設計判断の「ZZZ の数値スケール」の未検証点がそのまま消える）

ただし既定を変えると **Cookie 依存になる**（今は Cookie 無しでもショーケースは読める）。
スタレは Mihomo のほうが軌跡の最大Lvまで返るので、寄せるとしても原神・ゼンゼロだけ。
**まだ変えていない。** 検証済みの挙動を黙って変えたくないため。

### 9. スタレの詳細取得が重い

スタレの `avatar/info` は**所持キャラ全員分を1回で返す**（実測 1.35MB）。
1キャラ見るだけでも全部取ってから絞っている。原神・ゼンゼロは ID 指定で1体ずつ取れる。
今は1分キャッシュで足りているが、所持数が増えると効いてくる。

### 10. HoYoLAB の詳細キャッシュはメモリ上だけ

codex レビュー（2026-09-20）を受けて取得間隔つきキャッシュを入れたが、`hoyoCache` は
**プロセスが死ぬと消える**。MCP は使うたびに起動され得るので、セッションをまたぐと
スタレの1.35MBを取り直す。所持一覧はファイルに残しているので、詳細も同じように
ファイルへ落とすかは未決（サイズが大きいので、置き場と期限を決めてからにしたい）。
